# Shared Agent capabilities and useful background work

Baseline: main `67e9392dbb0eaf9bd696842056701f2b36cd0f37`, the verified Live Brain and conversational follow-through release. Main remains the upgrade baseline.

The existing foreground capability inventory and Initiative planner share an explicit family/skill contract. Metadata organizes the existing executors; it cannot grant permissions, select a provider or turn a read into a business action. Foreground readiness fields remain authoritative. The model chooses useful work from current situations and admitted tools; no arrival-to-action or transcript-to-announcement sequence is hard-coded.

## Acceptance criteria

1. Every existing foreground capability has an explicit parent and skill path. The six additional background leaves declare sources, read/preparation mode, existing executor, cost, retention, confirmation and verification. Unknown tools cannot inherit execution authority from a parent name.
2. Recent authorized transcripts remain observable when analysis is missing, stale or has no actions. A selected read supplies bounded actual transcript passages and saved analysis with freshness, interpretation labels and partial coverage. It performs no new analysis or research.
3. Completed Mission evidence is read from actual saved page excerpts, with matching canonical actions, completed Cloud receipts and collection authority. Source edits outside the displayed prefix still invalidate the result. No new research is claimed.
4. Owned products and recorded owned media metadata support private copy, promotion concepts and image briefs. Existing System-only Commerce scope is preserved. Metadata does not establish unseen image contents, a complete gallery or missing promotion; no image-provider request, publication or purchase occurs.
5. Task, reminder and personal-calendar reads use existing ledgers and current owner/Agent permissions. Calendar occurrences preserve their canonical recurring identity. Source reads never reconcile tasks, tick reminders, send invitations or mutate domain state. Existing Profile call situations remain peers in the context stream; this section adds no raw PSTN/SMS adapter.
6. A model-selected leaf actually runs through the existing Initiative queue. Its useful draft and exact read proof survive normalization into the same action, receipt, saved Chat post and live Brain projection. Continuation uses the existing composer and queue, repeats only the original declared readonly leaf, and receives current actual records plus the full saved owner request.
7. Sources are checked before and after inference and under a short serializable final transaction. Independent native database writers cannot change selected products/media/bindings between the final check and commit. Only a rolled-back serialization/deadlock decision may retry once; inference is never replayed in that retry.
8. Owner, Agent, conversation, participant, source and processing permissions are fresh at execution, delayed delivery and owner replies. Pause permits readonly inspection of an already authorized saved post; it cannot authorize inference or additional work. Source revocation still withdraws private results.
9. Actual browser tests exercise source-backed work and owner follow-through in desktop/mobile Chat and the existing Brain feed. No additional core activation switch, conversation engine or dashboard is introduced.
10. The frozen PR head, current validated main base, all applicable official checks, exact merge, post-merge workflows and original successful production ZIP are verified before release. ZIP bytes, manifest and every packaged source must match the merged tree.

## Read and delivery boundaries

Transcript and Mission source revisions include full canonical content/receipt evidence, not just displayed excerpts. Repeated source reads have no inference or domain effects. Meeting transcript reads retain the canonical Cloud-processing policy. A strict readonly compute preference reader avoids schema provisioning during source checks. Fresh remote privacy checks happen before database transactions; a final transaction accepts only an exact, short-lived request-local proof, with current meeting/session/preference identity. A cold delayed-delivery sweep refreshes an exact bounded candidate outside locks and rechecks it inside the final transaction.

The processing guard accepts an explicit, freshly validated server-owner context for canonical workers with no browser session. It does not impersonate a session or grant a guest owner access. Stored connection, credential and capability reads have a non-provisioning path; missing keys, malformed scope permissions and unavailable paired servers fail closed. Remote privacy reads reuse the existing authenticated transport, whose request audit/HTTPS queue bookkeeping can occur outside the final transaction; no new inference or domain mutation is performed by a source read. Local pairing authorization is included in the short-lived final proof, excluding heartbeat-only telemetry.

Meeting origin is retained through canonical meeting identifiers even if recording-library edits change the capture label. Explicit HomeServer-only processing stays blocked from Cloud even when a paired wrapper otherwise allows Cloud. Foreground and background processing guards use the same strict privacy path, and healthy HTTPS scope discovery uses the existing owner-aware transport.

Structured read results reach the existing private preparation model with coverage and interpretation limits. The durable workflow stores the actual prepared draft, canonical tool receipt, exact source revisions and semantic read/coverage fingerprints. It does not duplicate raw transcripts, page excerpts or media metadata into a separate memory store. The existing engagement memory can reuse authorized decisions/outcomes without treating silence as disinterest.

Current source permissions remain explicit. Analysis refresh, new web research, image generation, publication, spending, sending messages, calling, scheduling and other writes retain their existing domain request, quota and confirmation contracts. Declaring a child of a write-capable parent supplies no write authority.

## Evidence limits

Repository/browser fixtures and an original verified GitHub package establish this defined section. Installed hosting configuration, provider credentials, actual cron invocation and closed-browser scheduling still require an installed-account trace. Broader specialist scheduling, new content galleries, generalized app execution and raw connected-business financial retention are separate work; existing restricted remote-answer retention is unchanged.
