# S7 — App changes, control discovery and release inspection

The three handlers existed, but their execution guarantees did not match what Chat could promise. Confirmations did not retain the Agent principal, a zero conversation could omit the stored conversation constraint, expired external-action leases could run again, and exceptions returned an action to prepared state after uncertain effects. A substring search treated even `reconcile_pending: false` as pending. Raw control/release objects could enter Chat and missing fields could become false availability or empty declarations. Per-app reconciliation could widen to all owned apps.

The shared routing model now selects strict app-operation reads and bounded System App change plans. Existing preparation/confirmation services remain authoritative: no second confirmation store, scheduler, app registry or arbitrary invocation is added. Preparation stores the current owner, Agent, conversation and catalog identity/version and metadata fingerprint in existing JSON. Confirmation rechecks that scope, active account, ownership and catalog selection including exact active/previous release selection for rollback, before claiming the row, before and after every remote hop, and before saving the result. Existing row locks and execution tokens consume the request once. Uncertain or abandoned executions cannot run again through the same confirmation. Completed replays read the saved result and never claim a newly applied change. Old pending plans without durable scope require preparation again.

Canonical installation, release, hosting and permission services remain in use. Safe outcome summaries distinguish verified completion, explicit pending reconciliation, automatic rollback and unknown results; raw runtime objects, settings, native paths, source and error messages are excluded. A single-app reconciliation sends only that app key; an all-app plan requires explicit all scope. Existing legacy actions share the same service guarantees and reject ambiguous app/site matches. Opening Apps is a manual link rather than a claim that the browser navigated.

Control inspection selects exactly one installed app from the current strict App Manager response, validates live app identity, boolean compatibility, unique action/setting keys and hosting count, and returns only bounded declaration counts/keys/descriptions. Release inspection reads canonical catalog data without schema/seed writes. Owned/installed live reads strictly validate identity and rollback fields plus the existing version/channel/hash checks, rechecking ownership after the response. Failures are reported explicitly rather than hidden as no rollback. Capability questions perform no private read or preparation. The provider-level JSON instructions now honor the operation-specific routing contract instead of restricting the model to the obsolete inspect/continue-only schema.

Local evidence includes 64 canonical SQLite cases with a MySQL-syntax compatibility fixture and controlled network, 259 cases through actual typed/voice/streaming/legacy Chat endpoints with a controlled model, and the preceding S6 canonical read regressions. MySQL certification additionally covers live Agent reassignment, inactive accounts, zero-conversation bypass and uncertain external-action replay using the existing workflow. PR gates and exact merged-package verification are required before release. Provider, paired HomeServer and deployed-browser acceptance remain separate. S7 adds 3 assessed legacy handlers: 17 of 29, 12 remaining, with 37 individual capability IDs. HomeServer source is not changed or published.
