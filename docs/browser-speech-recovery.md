# Browser speech connection recovery

The Chat listening controller disabled voice after five unexpected browser aborts or three network errors. These are service/transport failures, not evidence that microphone permission was denied. The independent barge recognizer could also cancel the current spoken answer after three transient failures.

Only transient `aborted`/`network` failures now retain the current page's explicit listening intent and schedule a fresh recognizer with exponential backoff capped at 30 seconds. Native end/release is still required before any replacement starts. The processed microphone monitor is released during reconnect waits, and the UI shows reconnecting rather than listening. Real `onstart` clears the stale connection error. Barge transport recovery does not cancel an answer that is already speaking.

Offline notifications release capture and slow probes; online notifications expedite a new probe. Browser online status is only a hint and does not prove speech-provider availability, so offline hints do not permanently block probes. No Chat request, recorded message or saved draft is replayed by these events. Stop, page exit, capture-lease loss and expiry of the existing temporary reply window cancel recovery. Permission/service-policy denial, missing/ended audio capture and native sessions that fail to release still stop with an explicit diagnostic. Startup watchdog limits remain in place for recognizers that never start. No new speech provider, recording upload, credential, subscription or HomeServer change is introduced.

The voice asset URL and runtime build are updated so deployed browsers load the fix. The deterministic controller/lease suite covers sustained failures beyond the former cutoff, bounded waits, release ordering, offline hints, online recovery, barge continuity, permission failures, Stop and reply-window/page/lease fences. The real Chromium Chat test injects seven transient service failures into 20 consecutive typed/voice-context turns, checks cumulative final deduplication, and verifies offline/online recovery without capture restart after Stop or replay of a Chat turn. The speech service itself is controlled in these tests; actual browser-provider availability remains an environment acceptance check.

## Native startup regression

Commit `f7f775f` changed main Chat startup from immediate native `start()` plus an asynchronous monitor to waiting for `ensureProcessedMic()` before native `start()`. The monitor uses a separate `getUserMedia` stream for near-field/echo analysis; it is not the native speech recognizer's input. A delayed or unanswered monitor request therefore prevented native recognition from starting, and the native startup watchdog was also never armed. It additionally moved native startup out of the synchronous enable call. A pending-monitor fixture reproduces this failure on the previous production source.

Native speech now starts immediately alongside the optional monitor, restoring the earlier ordering for main listening and using the same ordering for barge-in. Monitor acquisition retains its generation and capture-ticket checks, so streams arriving after Stop, shutdown or lease loss are stopped. Capture leases, native-session release ordering, reconnect backoff, permission failures and draft isolation are unchanged. The native startup watchdog now applies even when the independent monitor never resolves. The voice asset and cache versions change to force deployment of this fix.

The controller/actual-lease suite exercises unresolved monitor startup, healthy listening with an unresolved monitor, bounded native startup failure, barge startup and late-stream disposal. The Chromium suite verifies immediate native startup in the enable call, an unresolved monitor across 15 seconds, and late-stream disposal after Stop. These reproduce and verify the startup dependency regression; they do not establish the cause of every real browser-provider network failure without diagnostics from that browser.
