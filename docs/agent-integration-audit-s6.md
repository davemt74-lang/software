# S6 — Cloud catalog, stored app health and live permission reads

## Concrete gaps

Catalog/health reads could create schema or seed/update the included catalog. Stored connection and runtime flags could be presented as current health. The old Chat health route could enter the hosting diagnostic helper, whose binding initialization can write a HomeServer binding during an apparent read. Permission reads defaulted missing arrays/counts to empty/zero, exposed raw remote errors and had no shared execution receipt. A hosting projection joined a current-user binding to a site without also checking the site's owner.

## Built behavior

The existing canonical catalog chain and connection reader accept an optional read-only mode, propagated through the versioned helpers. Existing UI/setup callers retain their defaults. Verified Chat catalog/health reads and automatic Brain context opt into read-only mode, skip schema creation/seeding, and report missing storage instead of repairing it. Hosting projections require matching binding/site ownership. The canonical stored health calculation is reused; Chat labels its observations and dates instead of claiming live runtime, route or TLS verification. Automatic context failures supply explicit failed-read evidence without raw error text. Live Hosting diagnostics remain on their existing explicit surface; the verified stored-health Chat read does not initialize a binding.

The shared capability model selects strict `system_apps_read` plans with known IDs, bounded filters and exact app selectors. No additional classifier is added. Catalog/health read current Cloud records and timestamped cached projections without remote operations. Permission reads require one exact known System App, current active ownership and an observed installed projection, then reuse the paired `apps.system.permissions.status` operation. Strict mode verifies app identity, unique permission keys, boolean states and counts matching the actual returned rows. Ownership, installation and catalog mapping are rechecked after a remote response; current owner/account/Agent/conversation authority is checked before and after the complete read. Grant/revoke and other consequential actions remain on existing confirmation services.

The three legacy Chat handlers use the same verified paths, preserving the VRSS/Feed alias and diagnostic question punctuation. The MySQL harnesses load the real active-account and conversation boundary for legacy reads. Responses expose bounded names, keys, observation dates, classification and permission states, excluding raw remote objects, tokens, native paths, stored error text and source content. Read results issue shared receipts for the existing diagnosis flow. Navigation remains a manual canonical Apps link, not proof of browser navigation. No new database, scheduler, permission grant, installation, HomeServer code or schema migration is introduced.

## Evidence and release gates

Local evidence: 44 cases using real SQLite catalog/ownership/install/hosting/connection data and canonical services, with a SQL write guard that rejects schema, seed and binding writes; only the network and tool-history infrastructure are fixtures. Cases cover foreign site bindings, unobserved and stale runtime, exact selection, ownership/installation restrictions, malformed/duplicate/contradictory permission responses, late revocation, failed automatic context and Profile isolation. The production typed/streaming/legacy endpoint fixture passes 223 cases using a controlled routing model. The recovery baseline and focused S4/S5/control regressions remain gates. Existing source contracts now check the actual shared executor and the no-implicit-hosting-binding path.

Required PR checks and exact merged-package verification complete scoped release certification. Live provider, paired HomeServer and deployment behavior remain acceptance checks.
