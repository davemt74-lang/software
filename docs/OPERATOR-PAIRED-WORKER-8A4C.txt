# Operator 8A.4C — paired HomeServer registration (simulation only)

Dependent on Cloud #856 and HomeServer #378. Adds an explicit server-side grant tied to the existing current HTTPS HomeServer pairing. One grant per owner; credential_id is random, the worker secret is independently random and AES-256-GCM encrypted with a separate 32-byte master key. The authenticated associated data binds the owner, credential, pairing device, exact pairing session hash and worker identity. No keys are stored in the registry or returned from the CLI.

Deployment is deliberately off by default. After all release checks pass, configure the private, untracked config.php with operator_worker_registration => ['enabled'=>false,'master_key_hex'=>'<64 hex characters from a secure random generator>']. Use a unique high-entropy key, not any existing app/relay/Twilio secret. Store it privately and back it up; loss requires explicit revoke/rotation, not silent replacement. Run php tools/operator-worker-admin-8a4.php install once using the Cloud CLI; the additive schema is not installed from HTTP. Enable registration explicitly only for a controlled non-billable test environment; php tools/operator-worker-admin-8a4.php grant OWNER_ID HS_DEVICE is a privileged, explicit one-account grant. The command does not send secrets, place calls or modify pairing. Disable registration globally by setting enabled false. Use php tools/operator-worker-admin-8a4.php revoke OWNER_ID to durably fence and erase the active worker secret, even if the device disconnected. Revoke before re-granting after session replacement.

POST /api/operator-worker-credential-8a4.php requires HTTPS, Content-Type: application/json, exact body {}, Authorization: Bearer <current HTTPS pairing session token>, X-HomeServer-Device: <exact paired hs-device>. It returns credential_id, owner_id, derived 32-hex device_id, fixed worker_id, secret_hex, capabilities and false live/execution flags. The same active grant can be retrieved again by the exact current paired device; this is intentional for lost response recovery. Use no cache, no logs, no browser exposure. Protect the existing pairing bearer as a credential. A production HomeServer credential retrieval/storage adapter remains to be implemented.

POST /api/operator-worker-registration-8a4.php accepts the exact 8A.2 canonical body and X-VP3-Operator-Signature, returning canonical signed JSON on HTTP 200. It matches the fixed path in #378. The handler caps body size, accepts POST over server-verified HTTPS only, requires explicit config enablement, returns generic errors and performs no schema installation. No forwarded-proto trust, browser session, cookie auth or CORS. PHP HTTPS must be set by the trusted web server. Registration authenticates the credential and checks current account activation, pairing/session status, exact device and session hash, and current grant under the same transaction as the registration receipt. Old/revoked/replaced credentials cannot replay even cached receipts. Pairing revocation prevents further reports; existing simulation registry metadata may remain until lease expiry. No production claim selection or execution is exposed. Production selection must recheck pairing in its own transaction, not trust the reporting lease alone.

Run tests/agent-operator-paired-worker-8a4.php in the isolated SQLite and dedicated MySQL CI stores. No real credentials, network or carrier use. Release gates still include real TLS endpoint deployment, HomeServer retrieval/secure storage, revocation propagation to all future live claims, background worker supervision, cost/consent checks, native Twilio service, and physical acceptance. No live dialing or LiveKit changes.
