# ML2B — VP3 music provider

## Implemented scope and release boundary

ML2B adds a versioned provider API and **Sites & streaming** management from Music Workspace. An authorized artist can register a standalone site, prove control of its HTTPS origin, explicitly select public recordings, and let visitors stream the canonical VP3 audio without a VP3 account or third-party cookies. The provider records anonymous, bounded listening evidence and delivery usage separately.

The implementation starts from main `180743e41ad40c249af6d27c64e0a7ba9cc932cf`, including merged ML1 #930 and ML2A #936 and the subsequent Brainstorming and call-review changes. The implementation PR records the exact candidate, applicable CI, reviewed browser artifacts, merge and packaged release. Local passing tests are not a claim about an unrun MySQL/browser check or a live host.

Stoneward's **Import Music from VP3** UI and source adapter remain ML2C. The combined recording pilot, deployed Apache/CDN behavior and physical-device playback remain ML2D. This phase does not activate private/paid visitor access, downloads, a royalty rate, financial accrual, payments, an artist analytics dashboard or managed website provisioning.

## Artist workflow

`music-workspace.php` links to `music-sites.php?workspace=ID`. Its owner/manager page provides:

1. Register a production or staging site with a label and exact HTTPS origin.
2. Copy the newly generated credential into the site's private backend settings. It remains in page memory only and is never saved in browser storage or displayed on a later page load.
3. Publish the supplied JSON verification response at the site's fixed `/api/vp3-music-site.php` endpoint and choose **Verify site**. ML2C will automate this setup in Stoneward. A custom site can implement the endpoint now.
4. Browse/search published public recordings and explicitly save the selected recording IDs. The view identifies unavailable selected references and allows removing them without publishing private content.
5. Reconnect with a fresh credential, change the origin, or revoke the connection. Reconnect and address changes preserve the site ID and selected references but stop existing grants and require new verification.

Only public, published, unarchived, correctly mapped recordings can be selected for visitor streaming. A private/draft album's title and ID are not exported through a public song. Artwork requires a public photo and an eligible parent chain; an ordinary storage URL is never exported.

Selections are explicit snapshots. Adding an album track does not add it to a site automatically. API catalog entries retain album ID and track number for the later consumer's selection/import UI. Selection sets contain at most 500 canonical recording IDs; ordering of a release is metadata, not inferred from UUID order. A changed selection revision invalidates existing site sessions conservatively. Saving the same set is a no-op and preserves its revision.

## Authority and connection lifecycle

The protocol is `vp3_music_provider_v1`; the schema is `music-provider-v1-20261126`.

| Authority | Allowed operations | Boundary |
|---|---|---|
| Signed-in owner/manager, current role and CSRF | Register, verify, rotate, move/revoke a site, inspect/select its public catalog | Selected Music Workspace only; current user and workspace state reloaded |
| Site backend bearer `vmp1_` + 64 lowercase hex characters | `catalog.read`, `selection.update`, `import.manifest` | No site administration, catalog editing, private audio or listener history |
| Visitor `mps1_` + 64 lowercase hex characters | One session's event reporting and renewal | No artist authority, account identity or other session access |
| Signed `mpd1` media ticket | GET/HEAD for one pinned asset/session | Five-minute expiry plus current database authority; no catalog enumeration |

Management credentials contain 256 random bits generated by the authorized client. The database stores their SHA-256 digests and issued-digest tombstones; a rotated/revoked credential cannot be issued again. The initial lifetime is 90 days. Site rotation requires a new credential and new origin proof. Stable site IDs and explicit selected references survive reconnection.

Verification uses the existing DNS-pinned HTTPS transport, fixed endpoint, public-address validation, no redirects, no proxy/environment credentials, bounded response and timeout. The response must match the current site ID, exact origin, protocol and challenge. Verification is performed before the short write transaction; the revision/challenge is checked again under lock. No arbitrary callback URL is accepted.

Initial registration supports public DNS HTTPS origins on default port 443, normalized lowercase, with no wildcard, path, user information, query or fragment. Staging is a distinct registration. This is an explicit runtime profile, not a claim that every hosting/proxy configuration is certified.

Every backend, begin, renewal, event and media authorization rechecks current creator account activity, workspace enablement, manager/owner authority, site state, credential lifetime, connection revision, selection revision/membership and recording publication. An owner can replace a departed manager's credential through a new reconnect/verification. Removing access never confers rights on a visitor through the artist's privileged account.

## Routes and request contract

All JSON replies include `protocol`, `correlation_id`, `ok`, and either operation results or `code`, `message`, `retryable`, and safe `details`. HTTP errors never expose storage paths, secrets, SQL or raw exceptions. JSON requests are objects, at most 32 KiB, with mandatory protocol and action; unsupported fields/versions fail explicitly.

| Route | Caller / methods | Operations |
|---|---|---|
| `api/music-provider-manage-v1.php` | Signed-in same-origin client; POST JSON with CSRF | `site.list/create/verify/rotate/change_origin/revoke`, `catalog.read`, `selection.update`, `import.manifest` |
| `api/music-provider-v1.php` | GET | Public discovery, canonical provider URL, installation ID and actual capabilities |
| Same route | Backend POST, `Authorization: Bearer vmp1_…`, no Origin | Catalog, explicit selection, selected import manifest |
| Same route | Visitor POST; `?site_id=…` supplies browser preflight context | `playback.begin`, `playback.renew`, `playback.events` |
| `api/music-provider-media-v1.php?ticket=…` | GET / HEAD / OPTIONS | Authorized exact audio bytes, single ranges and validators |
| `api/music-provider-artwork-v1.php?site_id=…&recording_id=…` | GET / HEAD / OPTIONS | Current selected public artwork only |

Owner requests supply integer `workspace_id`; lifecycle writes also supply a UUID `request_id` and, except creation, `expected_revision`. Creation takes `origin`, `label`, `environment`, and `credential`. Rotation takes a new credential; origin changes also take a new origin. The owner-only pending site projection includes its verification response. Backend projections never include that challenge or a management credential.

Catalog and manifest requests accept `offset` (initial 0), `limit` (1–50), and catalog title `search`. Results include `installation_id`, a safe `site`, `items`, selected `recording_ids`, and `next_offset`. Recording items contain stable recording/work/catalog/asset identities, metadata/work/catalog revisions, album/track placement, public metadata, artwork reference or null, availability and a nonauthoritative duration hint. An unavailable selected recording is a minimal reference; it is not silently deleted from the import manifest.

`selection.update` supplies `site_id`, UUID `request_id`, integer `expected_selection_revision`, and an explicit array `recording_ids`. The receipt is stored atomically with membership changes. Exact retries return the same result. Conflicting request reuse or stale revisions return 409. Retrying a lost response is the reconciliation mechanism; do not allocate a different request ID to guess whether a mutation succeeded.

### Visitor begin

Generate a fresh logical play UUID and random `mps1_` visitor key for a deliberate new play. Keep them in memory and reuse the exact frozen body when the begin response is lost. Do not send a site management bearer with this request.

```json
{
  "protocol": "vp3_music_provider_v1",
  "action": "playback.begin",
  "site_id": "<registered site UUID>",
  "recording_id": "<selected recording UUID>",
  "play_id": "<new logical play UUID>",
  "playback_key": "mps1_<64 random lowercase hex characters>",
  "source_surface": "player",
  "source_url": "https://artist.example.com/music.php",
  "position_ms": 0,
  "playback_rate": 1,
  "muted": false,
  "loop": false
}
```

The response contains the session ID, immutable recording/asset attribution, safe source context, pending state, zero accepted time, unknown-or-probed duration and `media.url`, `media.ticket_expires_ms`, MIME, byte size and ETag. No playback key is returned or stored as plaintext. The original begin receipt can contain an expired ticket after a delayed retry: renew the same session to obtain current delivery authority.

### Events and renewal

Both operations send `Authorization: Bearer mps1_…` and a JSON `site_id` and `session_id`. The URL's optional `site_id` must agree with the body and actual session; browsers use it for OPTIONS preflight.

An event uses `action: playback.events`, `event_id` UUID, positive consecutive `seq`, `event_type`, resulting `state`, `position_ms`, `elapsed_ms`, `cumulative_played_ms`, `playback_rate`, and optional boolean `muted`, `loop`, `observation_partial`.

Supported transitions are resume/playing, heartbeat/playing|paused|buffering, pause/paused, seek/seeking|paused|playing, waiting/buffering, ratechange/playing|paused|buffering, ended/ended, stop/stopped. The first event must establish resume/playing with zero cumulative time. Event IDs and sequences are immutable. Duplicate identical events return their original receipt; conflicts or sequence gaps return 409 with the next sequence when relevant. Never send a new sequence as a substitute for retrying an unacknowledged event.

Renewal uses `action: playback.renew` plus a UUID `request_id`. It preserves the session, original asset, source, counters and event sequence. A repeated renewal ID returns its original receipt, including its original expiry. Use a new renewal request ID only when requesting a genuinely later ticket. The consumer must refresh the transport URL without entering its new-play/telemetry restart branch.

## Measurement, source attribution and byte delivery

Begin, HEAD, preload, range fetches and byte delivery do not count as heard playback. A first accepted resume records a **client-reported start**, not proof that a person listened. Elapsed playing time is bounded by server time, media advancement, prior state, supported playback rate and 30 seconds per event. Paused or buffering time cannot finance a later interval; seeks and implausible movement do not create listening. Unverifiable delayed segments remain partial.

Metric `legacy_10s_80pct_v1` preserves 10 seconds as qualified engagement and accumulated elapsed listening of 80% of server-probed duration as completion. Position progress and natural ending are separate. Only exact pinned MP3 bytes currently provide a server-probed duration; other allowed codecs can stream with completion unknown. Neither engagement threshold creates a royalty obligation.

Visitor classes are `public_anonymous_unclassified` or `staging_test`. No VP3 cookie, Stoneward customer identifier, email, device fingerprint or personal history is imported. Owner preview cannot be inferred from anonymous public playback and is not falsely classified as independently verified audience. Source attribution includes registered site ID/verified origin separately from its reported page, surface and `page_verified: false`.

Only exact supported public paths are retained: `/`, `/index.php`, `/music`, `/music/`, `/music.php`, `/listen`, `/listen/`, `/listen.php`, `/track.php`, `/song.php`, `/album.php`, `/albums.php`, `/discography.php`. Queries/fragments are discarded. Credentials, malformed/foreign URLs and unknown paths produce a null page with an explicit reason. Raw page URLs are neither retained in a fallback nor hashed as hidden identifying data. The initial page stays fixed during renewal.

Assets require a canonical SHA-256 digest and size, a readable file beneath `/uploads`, an allowed MIME verified by fileinfo, and a maximum of 64 MiB. A legacy native `/audio` file remains playable through its existing player but is marked `audio_requires_repair` for this initial provider profile; the existing music file repair upload supplies an eligible canonical asset. Each delivery creates a bounded private temporary snapshot, verifies its exact digest, then serves that same open snapshot. A changed original cannot splice bytes into a previously authorized response. Technical replacements affect new sessions; an old session can continue its retained original asset while publication remains authorized. Missing/corrupt pinned bytes fail rather than switching recordings.

GET supports full, single bounded/open/suffix ranges and 206/416; HEAD ignores Range and sends full representation headers without a body. ETags identify the exact byte digest. A mismatching/weak/date If-Range falls back to the complete pinned representation. These semantics follow [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), sections 13.1.5 and 14.2. Multipart ranges are not supported.

Provider replies are `no-store, private, no-transform`. Media/artwork alone receive the scoped Apache/PHP cross-origin resource policy. Browser CORS allows only the exact current registered origin, never credentials; missing Origin is allowed for nonbrowser public transports and does not independently verify the originating page. Missing Referrer is not an access failure. Catalog management rejects browser Origin requests and keeps its credential on the backend. Public bootstrap starts no PHP session and runs no unrelated request maintenance.

Revocation blocks the next request, renewal and event acceptance after current state is read. No shared caching is authorized. An already admitted response can finish its bounded snapshot, and bytes already delivered cannot be recalled. Canonical unpublish/private/archive writes mark active sessions permanently withdrawn in the same transaction, so republishing cannot revive them. Finished historical sessions retain their final state and evidence.

## Bounds, storage and recovery

| Bound | Initial value / meaning |
|---|---|
| Site registrations | 20 per workspace; production and staging distinct |
| Selected recordings | 500 per site; no automatic expansion |
| Credential / playback session / media ticket | 90 days / 24 hours / 5 minutes |
| Event / renewal receipts | 10,000 / 512 per session |
| New playback rate | 300 per site per rolling minute; known begin retries do not allocate again |
| Active session admission | 500 per site with recent activity within two minutes |
| Media requests / reserved bytes | 2,048 / 2 GiB per session |
| JSON body / source page input / asset | 32 KiB / 2,048 characters before sanitizing / 64 MiB |

These are engineering limits, not paid plans, storage allowances or commercial overage terms. Delivery reservations remain consumed if the response aborts; the separately acknowledged `emitted_bytes` value means bytes emitted by the server, not bytes received or heard. Unfinished delivery rows represent incomplete accounting coverage. HEAD/416 reserve no body bytes. Delivery updates have their own exactly-once receipts and cannot increment listening.

New tables contain provider settings/installation identity, site registrations, issued credential digests, selection membership, management receipts, playback sessions, playback/renewal receipts and delivery reservations/completions. Relevant primary, unique and foreign-key constraints are checked, with native MySQL and SQLite implementations. Writes use current row locks/SQLite write reservation; receipt failures roll back state.

`playback.begin` owns its transaction and rejects a caller-owned transaction with `transaction_boundary_required` (409) before mutation. It resolves the immutable site-to-workspace mapping before opening its transaction, then locks the canonical workspace followed by the site before its first eligibility snapshot. This shares the catalog writer's mutex: an earlier begin is included in a later withdrawal, and a begin waiting behind withdrawal reads the committed publication state. A caller's older MySQL repeatable-read snapshot cannot create a latent grant that revives on republication. Other writes retain nested savepoints, including events, renewal and delivery accounting.

Only the explicit setup/web upgrade/CLI migration creates schema. Report mode runs read-only, exposes counts and protocol state, and never exports signing keys, tokens, customer identities or page URLs. Existing ML1 catalog and ML2A/native history are not rewritten into provider events. The installation identity and signing key must remain with the matching database on an intentional restore. A clone is a different deployment and needs separate identity/registration before use; automated clone provisioning/restore is not shipped here.

No raw-event or retained-asset purge runs automatically. D-05 retention and D-10 commercial service allowances remain open. Do not delete retained ML1 audio while active sessions may need it. See [deployment procedure](../MUSIC-PROVIDER-DEPLOY.txt) for required backups, config, host headers, token-log redaction, upgrade and live checks.

## Acceptance and score

The phase's implementation score covers current authority/isolation, explicit catalog selection, migration/report integrity, exact retry and concurrent receipt behavior, timing bounds, asset pinning/ranges/revocation, source/private projection, responsive owner controls, regression gates and a verified source/package. Real SQLite/PHP HTTP, native MySQL and installed-browser CI results must be recorded against the actual candidate before claiming completion.

Tests are `music-provider-management-v1.php`, `music-provider-playback-v1.php`, their guarded native MySQL wrappers, `music-provider-concurrency-v1.php` with separate-process PDO races on both databases and a deterministic native MySQL publication race through the canonical catalog writer, `music-provider-api-v1.mjs`, and `music-provider-browser-v1.mjs`. The existing Music workflow also retains ML1/ML2A/API/player/browser regressions. [Implementation PR #939](https://github.com/davemt74-lang/software/pull/939) records final counts, exact workflow URLs, the actual merge and verified package; a local MySQL/browser SKIP is never a pass.

The later combined pilot must still demonstrate actual Stoneward source mapping, player and supported Agent/canvas consumers, renewal without local restart, privacy epochs, production Apache/CDN/media headers and physical iPhone/Android behavior. Deployment, production migration and backup restoration require their own observed evidence.
