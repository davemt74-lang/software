# S5 — user-app registry, manager and workspace diagnostic reads

The registry and manager projected missing/malformed remote lists as empty data. Manager failures could return unhandled, allowing an explicit local request to fall through. Workspace lookup chose the first substring match, treated missing validation as a failed project, and exposed broad diagnostic/metadata objects without shared execution evidence.

S5 adds strict `apps_read` plans to the existing shared capability model, with no additional classifier call. It reuses the canonical owner HomeServer app services, with opt-in strict read validation so existing UI/sharing callers retain their compatibility. Known capability IDs, bounded name/key filters, manager state filters and a single exact workspace selector are validated. Unknown, absent or ambiguous app selection lists current registry choices and cannot call workspace status. Reported validation true, false, absent and a failed/malformed read remain distinct. Inspecting a workspace never runs validation/build/install.

The adapter checks current owner, active account, named Agent and exact conversation before and after the read. It returns bounded name/key/state and diagnostic counts, excluding raw app data, source, file metadata, native paths, settings, credentials and remote error text. A manual canonical Apps link is separate from a receipt: a completed read is not proof of browser navigation. Existing Chat result authorization remains in place. All three legacy entry points use this same read path and issue shared receipts for diagnosis.

Local validation: 45 focused cases use actual SQLite owner/Agent/conversation services and the production registry, manager, workspace and transport validation functions, replacing only the network. The 190 production typed/streaming/legacy Chat cases use a controlled routing model. Cases cover strict plans, unknown/duplicate names, foreign keys, malformed/empty/denied/offline results, false/absent validation, late authority changes, source redaction, read-only operation allowlist, legacy entries and transport parity. The recovery baseline and existing 44 media, 13 workflow and 16 scheduling regressions pass. PR checks and exact merged ZIP verification are the final release gates. Live paired app behavior remains deployment acceptance.

See `agent-integration-audit-plan.md` for all 29 legacy handlers, phase order and separate capability counts. S5 adds three assessed handlers (11 total, 18 pending) and three capability IDs (31 total). No schema change or HomeServer source publication is required. Cloud catalog, health, permissions and consequential app controls remain separate sections; their existing executors are not disabled or falsely described as unavailable.
